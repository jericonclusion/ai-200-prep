Answer and explanation reviewed against the linked product documentation.

Current question: The Stellmarsh nightly scorer pods on `stell-batch` are in `CrashLoopBackOff`: each container exits about 20 seconds after starting, and Kubernetes keeps restarting it. `kubectl logs <pod> --previous` (`-p`) returns the stdout/stderr of the **previous, terminated instance** of the container — exactly what you need in a crash loop, where the *current* instance has just restarted and its log stream is empty or about to die again. They tell you *that* it crashed, not *why* the process exited. - **`az aks update --attach-acr`** — Registry integration fixes `ImagePullBackOff` (401s from the registry). These pods pull fine and *start*; the failure is inside the running process, so registry permissions are irrelevant.

ai200-s3-06-tarnwell-redis-getex

Answer and explanation reviewed against the linked product documentation.

Current question: You must implement the Tarnwell caching requirement in Azure Managed Redis: every read of a cached concierge answer must also reset that entry's remaining lifetime to 1 hour, in a **single round trip**, while unread entries still expire on their own. Which command should the Python service use on the read path?

`GETEX` retrieves a key's value **and atomically updates its expiration in the same command** — `GETEX answer:<hash> EX 3600` returns the cached answer and resets the TTL to 3,600 seconds. That produces exactly the required *sliding expiration*: popular answers are refreshed on every read and stay warm, while entries nobody reads keep their last TTL and expire naturally. One command, one round trip. **Why not the other options:** - **Plain `GET`** — Reading with `GET` does not touch the TTL, so an answer written once always dies 1 hour after the *write*, no matter how popular it is. That is absolute expiration, not the required sliding behavior. - **`PERSIST` + `GET`** — `PERSIST` *removes* the expiration entirely, so entries never expire again — violating "unread entries must still expire" — and it is two round trips (or needs a pipeline) instead of one. - **`TTL` + conditional `GET`** — `TTL` only *inspects* the remaining lifetime; it never extends it. This adds a round trip, still lets hot entries expire mid-popularity, and solves nothing.

ai200-s3-10-gantrell-appconfig-snapshot

Answer and explanation reviewed against the linked product documentation.

Current question: You must implement the Gantrell configuration requirement: each release must promote exactly the set of ~40 App Configuration key-values tested in staging, as one immutable named unit; rollback must restore exactly the previous unit; and later edits to individual keys must not affect what already-released instances load. What should you do?

An App Configuration **snapshot** is precisely the required artifact: a **named, immutable, point-in-time subset** of the store's key-values, defined by key/label filters. Creating a snapshot at release time freezes all 40 `Valuation:*` keys as one unit; instances that load from the snapshot always see exactly that tested set, no matter how the live key-values change afterward. ai200-s3-12-gantrell-kql-argmax

Answer and explanation reviewed against the linked product documentation.

Current question: You must build the Gantrell operations dashboard query: from `AppTraces`, return **one row per property** — the most recent valuation trace for that property, with **all** of its columns. The property identifier is in `Properties.propertyId`. Which KQL query should you use?

`arg_max(TimeGenerated, *)` is the KQL aggregation built for "latest row per group": within each `by propertyId` group it finds the row with the maximum `TimeGenerated` and, because of the `*`, returns **that entire row** — every column, exactly as the dashboard needs. The `extend ... tostring(Properties.propertyId)` first materializes the grouping key from the dynamic `Properties` column, since dynamic sub-properties must be converted to a scalar type to be used in `by`. **Why not the other options:** - **`summarize max(TimeGenerated) by propertyId`** — Returns only two columns: the property ID and a timestamp. `max()` aggregates a single value; it does not carry along the rest of the winning row, so the valuation status, message, and other columns are lost. - **`order by ... | take 1`** — Sorts the *whole table* and keeps a single row overall — the most recent trace in the entire system, for one property. The dashboard needs the most recent row for **each** property. - **`distinct propertyId, Message`** — Returns every unique combination of property and message with no notion of recency: old and new valuations for the same property all appear, and all other columns are dropped.

ai200-s3-16-ordering-dockerfile-cache

Made the otherwise optional position of CMD explicit for deterministic grading.

Current question: Caldermere Insurance builds a Python FastAPI inference image in CI on every commit. Dependencies in `requirements.txt` change rarely; application source changes on almost every build. You must order the Dockerfile instructions so that a source-only change reuses the cached dependency layer instead of re-running `pip install`. Place the instructions in the correct order. Use the project convention that the startup CMD is the final instruction.

Docker's build cache is invalidated **top-down**: the first instruction whose input changes forces every later layer to rebuild. The ordering therefore runs from least- to most-frequently changing: 1. **`FROM` + `WORKDIR`** — Every Dockerfile begins with the base image; `WORKDIR` establishes the path the later `COPY` and `RUN` instructions rely on. 2. **`COPY requirements.txt .`** — Copy *only* the manifest, so the next layer's cache key depends on nothing but this one file. 3. **`RUN pip install ...`** — The expensive step. Because its inputs are just the base layers and `requirements.txt`, a build where only source changed reuses this layer straight from cache. 4. **`COPY src/ ./src/`** — The volatile source comes *after* the install; changing it invalidates only this cheap layer and the ones below it. 5. **`CMD [...]`** — Metadata-only and effectively free; conventionally last, it defines how the final image starts. **Why not the other options:** - The classic mistake is a single `COPY . .` **before** `pip install` — then any source edit changes the copy layer's checksum, invalidating the install layer, and every CI build re-downloads and compiles all dependencies. - Installing dependencies before copying `requirements.txt` cannot work at all: the manifest is not yet in the build context's filesystem when `pip` runs.

ai200-s3-25-servicebus-receive-mode

Answer and explanation reviewed against the linked product documentation.

Current question: A Python worker consumes invoice-processing jobs from an Azure Service Bus queue with: ```python receiver = client.get_queue_receiver( queue_name="transcribe-jobs", receive_mode=ServiceBusReceiveMode.RECEIVE_AND_DELETE, ) ``` When a worker crashes mid-job, that job is **gone** — it is never processed by any worker. Jobs must be processed at least once even if workers crash. What should you do?

`RECEIVE_AND_DELETE` is **at-most-once** delivery: the broker deletes the message the moment it hands it over, so a crash between receive and completion destroys the only copy. `PEEK_LOCK` (the SDK default) is the **at-least-once** mode: the message stays in the queue under a time-limited lock while the worker processes it, and it is removed only when the worker explicitly calls `complete_message` after success. If the worker crashes, the lock simply expires and the broker makes the message available again for another worker — exactly the required behavior. **Why not the other options:** - **`try/except` + re-send** — An exception handler never runs when the process crashes, the VM dies, or the container is OOM-killed — precisely the failures described. The window between broker-side deletion and durable re-send is exactly where jobs vanish. - **Duplicate detection** — Deduplicates messages with the same `message_id` *on the send path*. It has no record of what consumers processed and cannot resurrect a message the broker already deleted on receive. - **`max_delivery_count`** — Counts *failed peek-lock delivery attempts* before dead-lettering. In RECEIVE_AND_DELETE mode every delivery succeeds from the broker's perspective (the handoff completed), so this setting never comes into play.

ai200-s3-26-eventhubs-consumer-groups

Answer and explanation reviewed against the linked product documentation.

Current question: Thornebridge Energy streams meter telemetry into an Azure Event Hub. Two independent applications read the stream: a real-time anomaly scorer and an archival service. Both were configured to read from the `$Default` consumer group with the same checkpoint container, and now each application receives only part of the stream — the two apps steal partitions and overwrite each other's checkpoints. What should you do?

A **consumer group** is an independent *view* (cursor) over the same event stream — this is precisely the mechanism Event Hubs provides for multiple downstream applications. Instances *within* one consumer group cooperatively balance partitions and share checkpoints; two *different applications* in the same group therefore look like one scaled-out app and fight over partitions and offsets, which is the observed failure. With one group (and one checkpoint store) per application, each app independently reads 100% of the stream at its own pace, and scaling instances within an app keeps working as designed. **Why not the other options:** - **A second event hub with double-send** — Duplicates ingestion cost, forces every producer change, and creates two streams that can drift (one send succeeds, the other fails). Consumer groups exist so a single stream can be read many times. - **More partitions** — Partition count controls parallelism *within* a consumer group; both apps in `$Default` would still balance the (now larger) partition set between themselves and still each see only a subset. The problem is shared cursors, not partition scarcity. - **Service Bus queue** — A queue is *competing consumers*: each message is delivered to exactly one receiver, which is the very behavior to eliminate. (Topics/subscriptions would fan out, but abandon Event Hubs' high-throughput streaming, offset replay, and checkpointing that a telemetry pipeline relies on.)
